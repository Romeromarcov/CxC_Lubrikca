# 1.1 — Inventario de los fallbacks silenciosos

Fase 1 del plan de blindaje. Reejecutable con:

```bash
python scripts/auditar_fallbacks.py --json docs/blindaje/fallbacks.json
```

El script clasifica cada `except` amplio y cada valor por defecto numérico de
`src/cxc/` en tres categorías. La clasificación automática es un filtro, no un
veredicto: abajo está la revisión a mano de todo lo que el filtro marcó fuera
de `app.py`, más las funciones de `app.py` con más concentración.

## Los tres criterios

- **Legítimo** — el dato es opcional de verdad y el default no llega a un
  saldo. Incluye el patrón *centinela*: se asigna `0` y se descarta en la línea
  siguiente (`if v <= 0: return None`). El cero nunca sale de la función.
- **Ruidoso** — debería dejar rastro y no lo deja. No inventa un número, pero
  hace que un fallo se vea igual que un éxito. Costo de arreglo: bajo, es
  agregar un `logger`.
- **Mina** — devuelve un número donde no hay dato, en un camino de dinero. Es
  la categoría de la que salieron los cuatro bugs de "sin datos no es cero".

## Minas confirmadas a mano, por severidad

### ALTA — el reporte de saldos muestra ceros cuando Odoo no responde

**`FastPriceResolver.precio` y `.volumen`** — `src/cxc/web/app.py:4525-4544`

```python
if self._fallback:
    try:
        return self._fallback.precio(producto, lista, fecha)
    except Exception:
        pass
return Decimal("0")
```

Es el resolvedor que usa `_get_reporte_saldos_sync`, el reporte principal. Si
el producto no está en el mapa precargado y la consulta a Odoo falla —el
`SSLEOFError` que ya se vio en producción—, el producto vale **cero**. Un
teórico de cero hace que la orden aparezca **saldada**: el saldo desaparece del
reporte en vez de mostrarse como indeterminado.

Es exactamente el escenario que la Fase 4 pone a prueba ("con Odoo fuera,
ninguna página debería mostrar ceros como si fueran saldos"). El balance ya se
abstiene; este camino no.

*Arreglo:* que `precio()` levante `PrecioNoDisponible` y que el reporte marque
la orden como no evaluable. **Costo: medio** — hay que decidir qué muestra la
página para una orden sin precio resoluble.

### ALTA — un fallo de red se disfraza de "no hay regla de precio"

**`OdooPriceResolver._precio_fijo_en_lista`** — `src/cxc/odoo/price.py:150`

```python
except Exception:
    rules = []
```

`rules = []` significa después "no hay regla en esta lista", que dispara toda
la cadena de fallback: otras pricelists, luego el precio de ficha, luego
`precio_fallback` (la fórmula con diferencial fijo). Un timeout de Odoo entra
por la misma puerta que un producto sin precio configurado, y el sistema
valora la línea por fórmula creyendo que hizo lo correcto.

Esto se enlaza con el ítem de deuda `OdooPriceResolver sin calibrar para Odoo
18`: hoy no se sabe **cuántas** líneas se valoran por fórmula, y de las que se
valoran así, cuántas es por falta de precio y cuántas por un fallo de lectura.
La 1.2 mide eso.

*Arreglo:* separar `None` (no hay regla) de la excepción (no pude leer), y
propagar la segunda. **Costo: bajo.**

### ALTA — el precio de ficha ilegible vale cero

**`OdooPriceResolver.precio`** — `src/cxc/odoo/price.py:255`

```python
except Exception:
    precio_ficha = Decimal("0.0")
```

Último eslabón de la cadena. Si falla la lectura de
`product.template.list_price_usd`, el precio queda en `0.0` y de ahí sale el
teórico. Mismo efecto que la mina anterior, un nivel más abajo.

*Arreglo:* propagar. **Costo: bajo.**

### ALTA — una lista desconocida se resuelve como Lista USD

**`OdooPriceResolver.precio`** — `src/cxc/odoo/price.py:200`

```python
except Exception:
    pricelist_id = self._pricelist_ids.get("USD", 4)
```

Si el identificador de lista no es numérico ni está en el mapeo, se valora
contra la lista 4. Es la forma genérica del caso que ya apareció con la lista
histórica usada para VES y USD indistintamente: no falla, da un precio, y el
precio es de otra lista.

*Arreglo:* levantar. Una orden con una lista que no se reconoce no se puede
valorar, y decirlo es más barato que valorarla mal. **Costo: bajo**, más el
trabajo de ver qué órdenes caen ahí hoy (lo mide la 1.2).

### ALTA — el teórico ausente se muestra como saldo cero

**`_saldos_4_columnas_item`** — `src/cxc/web/app.py:5590-5602`

```python
saldo_teorico_bs  = max(0.0, float(item.get("ves_neta_teorica_iva") or 0.0) - pagado_bcv)
saldo_teorico_usd = max(0.0, float(item.get("usd_neta_teorica_iva") or 0.0) - pagado_binance)
```

Dos defectos en la misma línea, y se refuerzan:

1. Si la clave del teórico falta —la orden nunca pasó por el cálculo— el
   minuendo es `0`, y la orden queda con saldo cero: **cobrada**.
2. El `max(0.0, …)` tapa el negativo. Un saldo negativo es un sobrepago o un
   teórico mal calculado, y las dos cosas hay que verlas. Acá se recortan a
   cero sin dejar rastro.

*Arreglo:* distinguir el teórico ausente (→ la orden no es evaluable) del
teórico cero real, y dejar pasar el negativo hasta una columna que lo muestre.
**Costo: medio.**

### MEDIA — el equivalente se congela con la tasa equivocada

**`resolver_tasa_bcv_vinculacion`** — `src/cxc/web/app.py:7250-7266`

Dos `except` mudos seguidos. Si falla `repo.get_orden`, la orden queda `None` y
por lo tanto "no es histórica" → tasa BCV-USD. Si falla la lectura de la tasa
euro, misma salida. En los dos casos se **congela** un equivalente en la
Vinculación con una tasa que no es la que correspondía, y congelado significa
que no se corrige después.

*Arreglo:* propagar y no crear la vinculación. Es una operación puntual, un
error acá es barato; un equivalente mal congelado no. **Costo: bajo.**

### MEDIA — el gate de Recompra cambia de regla en silencio

**`_objetivo_teorico`** — `src/cxc/engine/runner.py:110`

```python
except Exception:
    return None
```

`None` hace que el llamador caiga a `monto_total`, el precio de lista **sin**
descuentos. Es conservador (exige más para dar por pagada la orden anterior),
así que no regala plata, pero cambia la regla del gate sin avisar. Un fallo de
lectura del repositorio y una orden sin teórico calculado se ven idénticos.

*Arreglo:* distinguir los dos casos; el segundo sigue devolviendo `None`, el
primero propaga. **Costo: bajo.**

### YA REGISTRADA — el `36,5 / 38,0`

`src/cxc/web/app.py:2210`. Es la mina que el plan pone en la Fase 2.1. Se deja
anotada acá para que el inventario esté completo, pero **ya deja rastro**: la
línea 2204 registra un `logger.error` explícito antes de devolver el default.
No es silenciosa; es incorrecta. Su arreglo es la 2.1, que arrastra los 42

## Falsos positivos verificados — el código que ya está bien

Vale nombrarlos porque son el modelo a seguir y porque, si no quedan
descartados por escrito, el próximo inventario los va a volver a levantar.

**`src/cxc/rates.py` — el patrón centinela.** Los `fila.get(clave,
Decimal("0"))` están seguidos de `if v <= 0: return None`. El cero es un
sentinel interno que nunca sale de la función; la ausencia sale como `None`,
que el llamador está obligado a mirar. Es el patrón al que hay que llevar las
minas de arriba.

**`src/cxc/reconciliation/reconcile.py` — la bandera que lleva la ausencia.**
`NetoFacturado` tiene un campo `facturada: bool` separado del monto. Una orden
sin facturas devuelve `monto_facturado=0, facturada=False`; una factura de cero
devuelve `facturada=True`. Los cuatro sitios que el filtro marcó son
acumuladores (`montos.get(so, 0) + m`) o lecturas respaldadas por esa bandera.

**Acumuladores en general.** `d[k] = d.get(k, 0) + valor` es la forma normal de
sumar en un diccionario y no inventa nada: el cero es el neutro de la suma, no
un dato faltante. `client.py:643` (`if fid > vigentes.get(origen, 0)`) es la
misma idea con un máximo.

## Mina 9, encontrada después: una regla vencida que gana sobre la fecha

Ésta apareció al medir las otras, y es la más interesante del inventario porque
**el clasificador no podía cazarla**.

`_precio_fijo_en_lista` (`price.py:174-177`) busca entre las reglas de precio la
que calza con la fecha pedida y, si **ninguna** calza, devuelve `rules[0]` igual:

```python
if matched:
    matched.sort(key=lambda x: x[0], reverse=True)
    return matched[0][1]
return to_decimal(str(rules[0]["fixed_price"]))   # <-- la mina
```

O sea que nunca devuelve `None` mientras exista alguna regla para ese producto en
esa lista, aunque todas hayan vencido hace meses. Y `usa_fallback_ves`/`_usd` —la
única señal que dice "este teórico no es confiable"— se marca **solo** cuando
devuelve `None`. Una lista con todas las reglas vencidas entrega precios de abril
con la misma cara que una lista al día.

Por qué el clasificador la dejó pasar: `scripts/auditar_fallbacks.py` busca dos
formas, un `except` que no hace nada y un centinela numérico por defecto. Esto no
es ninguna de las dos. **Devuelve un dato real, verdadero para otra fecha.** No
hay nada sintáctico que lo distinga de un `return` legítimo, y la única forma de
verlo fue medir montos y preguntarse por qué no cerraban.

Costo medido: 789 órdenes valoradas con una lista vencida por el reporte de
saldos, 194.532,51 VES y 115.805,93 USD de desvío bruto — pero eso es el costo del
defecto que esta mina **oculta** (`app.py:4434` sin `_primer_id_activo`), no de la
mina en sí. La mina es lo que hizo que nadie lo notara en cinco meses. Ver
[3](3-escenarios.md) y [6](6-deuda-medida.md).

## Lo que quedaba para la 1.2, y cómo salió

Las minas de `price.py` no se podían priorizar bien sin saber **cuántas líneas se
valoran hoy por fórmula** en vez de por precio de lista, y cuántas de esas son por
falta de configuración y cuántas por un fallo de lectura.

La medición se hizo, y la primera vez **la hice mal**: publiqué 1,2 % de las
órdenes y bajé el ítem a Media. Al reejecutarla el número se movió sobre datos que
nadie tocó, y perseguir esa diferencia fue lo que destapó la mina 9. La cifra
corregida es **1,5 % de las órdenes** con algún producto sin regla de precio —el
problema de configuración, acotado— contra **789 órdenes** valoradas con la lista
equivocada, que es el problema real. El relato completo del error está en la
[3](3-escenarios.md#cómo-apareció-y-qué-medí-mal).
